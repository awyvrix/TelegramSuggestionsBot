# Аудит TelegramSuggestionsBot

**Объект:** `TelegramSuggestionsBot-main.zip`  
**Срез:** исходники из архива, состояние на 08.11.2026  
**Объём:** около 2 тыс. строк Java, 40+ исходных классов, Gradle, TelegramBots 10.3.0, Java 21.

## Краткий вывод

Проект не выглядит хаотичным: есть отдельные пакеты для команд, модерации, публикации, данных, расписания и конфигурации. Для небольшого личного бота это неплохая отправная точка. Главная проблема — границы пакетов не совпадают с границами ответственности: большая часть подсистем связана через `static`-поля `Main`, а состояние модерации и публикации меняется в нескольких потоках без единой модели транзакций.

Наиболее опасные места:

1. **Предоставленный архив не собирается в текущем виде:** `CommandsInit` ссылается на четыре класса, исходников которых в архиве нет, а их пакет исключён через `.gitignore`.
2. **Публикация неустойчива к ошибкам Telegram API:** очередь извлекает элемент до подтверждения отправки; при исключении задача может потерять элемент, а рабочий поток — завершиться.
3. **Очередь модерации не переживает перезапуск:** `submissions` не сохраняется, хотя кнопки модерации и признак `onModContent` переживают штатное сохранение.
4. **Есть ошибка в сетевой статистике:** время начала простоя фактически никогда не устанавливается.
5. **Есть несколько реальных сценариев падения:** пользователь без Telegram username, ошибки повторного нажатия/устаревших callback-кнопок, отправка медиа из группового чата.
6. **Параллельный доступ к состоянию организован непоследовательно:** `ConcurrentHashMap` используется только для внешней карты пользователей, но сами объекты пользователей, `HashSet` и `HashMap` потокобезопасными не становятся.

Полная Gradle-сборка в этой среде не была выполнена: wrapper попытался скачать Gradle 9.3.0, но соединение с `services.gradle.org` недоступно. Однако отсутствие классов `fun` подтверждается непосредственно содержимым ZIP и статическими импортами в коде.

## 1. Баги, которые точно есть

### 1.1. Неполный исходный архив не собирается

`CommandsInit.java:8–11` импортирует `Gos`, `LoreReport`, `Number` и `Object` из `net.awyvrix.bot.commands.custom.fun`; `CommandsInit.java:37–44` безусловно создаёт эти классы при `FUN_MODE == true` (по умолчанию `true`). При этом `.gitignore:7` исключает весь каталог `src/main/java/net/awyvrix/bot/commands/custom/fun/`, и в предоставленном ZIP этого каталога нет.

Следствие: при компиляции будут ошибки отсутствующих пакета/классов. Исправления: либо включать эти исходники в репозиторий, либо действительно вынести fun-команды в отдельный необязательный модуль/зависимость, либо убрать импорты и регистрацию из основной сборки. Простого `FUN_MODE = false` недостаточно: Java всё равно должна разрешить импорты и типы.

### 1.2. `NetworkMonitor` не записывает время начала простоя

`NetworkMonitor.java:44–47`:

- сначала `downStart` устанавливается в текущее время;
- затем сразу проверяется `if (downStart == 0)` для заполнения `downStartTime`.

После первой строки `downStart` уже не равен нулю, поэтому `downStartTime` остаётся `null`. После восстановления `downtimeUpdate()` записывает `NetworkReport` с `startTime == null` (`NetworkMonitor.java:53–58`). В `/report` поле будет отображаться как `null`.

Нужно объединить присваивания в один блок: при первом переходе в состояние недоступности одновременно записывать и epoch-время, и `LocalDateTime`/`Instant` начала простоя.

### 1.3. После одобрения модерации запись остаётся в `submissions`

`ModerationHandler.reject()` удаляет запись (`ModerationHandler.java:43–46`), а `approve()` получает её, добавляет в очередь и обновляет рейтинг, но не вызывает `submissions.remove(submissionId)` (`ModerationHandler.java:51–61`).

Следствие: каждая одобренная заявка остаётся в статической `HashMap` на всё время работы процесса. В ней хранятся `Submission` и связанные с ним строки/медиа-данные. Память постепенно расходуется, а повторный callback для того же ID всё ещё может повторно провести `publisher.submit(...)` и повторно начислить статистику/рейтинг.

Запись нужно удалять при успешном переходе в `APPROVED`, но не до того, как переход состояния зафиксирован. Лучше заменить простую карту на явную модель состояния заявки и атомарную операцию перехода.

## 2. Баги, которые могут быть

### 2.1. Состояние не защищено от одновременного доступа

Это системная проблема, а не одна конкретная строка.

- `Main.consume()` обрабатывает входящие команды и callback-и (`Main.java:90–109`).
- `ProcessorThread` параллельно исполняет задачи (`ProcessorThread.java:17–28`).
- `UpdateUserTask` изменяет `User.actions` (`UpdateUserTask.java:26–31`), а `MediaProcessor` одновременно читает и уменьшает это поле (`MediaProcessor.java:74–79`, `109–112`).
- `SetSnapshot` хранит обычный `HashSet` и отдаёт наружу прямую ссылку на него (`SetSnapshot.java:6–20`). Эти наборы изменяются обработчиками, пока `DataManager.save()` и `BackupDataManager.backup()` копируют их (`DataManager.java:27–56`, `BackupDataManager.java:28–64`).
- `UserData.users` — `ConcurrentHashMap`, но сами `User` содержат обычные `HashSet` тегов и публичные изменяемые поля (`User.java:6–12`).
- `ModerationHandler.submissions` — обычный `HashMap` (`ModerationHandler.java:20–22`).
- `NetworkMonitor.networkReports` — обычный `ArrayList`; `volatile` у ссылки не делает список потокобезопасным (`NetworkMonitor.java:26–27`).

В зависимости от порядка событий возможны потерянные изменения `actions`, неконсистентные снимки, `ConcurrentModificationException` при сериализации тегов, ошибки при чтении истории сети и повреждённая логика модерации. `ConcurrentHashMap` решает только конкурентный доступ к самой карте, но не к объектам внутри неё.

Отдельно: `UserData.getOrCreate()` реализован через `containsKey()` + `put()` (`UserData.java:9–12`). При параллельном создании одного ID второй `User` может заменить первый. Лучше `computeIfAbsent()`.

### 2.2. Сохранения могут конфликтовать и не являются атомарными

`DataManager.save()` напрямую перезаписывает `data.json` (`DataManager.java:27–56`). Метод вызывается как минимум из обработчика `/save`, из `PublisherTask` и из shutdown hook (`Main.java:63–70`, `PublisherTask.java:37–40`). Если вызовы совпадут, два потока могут одновременно открыть один файл на запись.

Кроме того, запись сразу идёт в конечный файл. Аварийное завершение процесса во время сериализации может оставить усечённый JSON. Копии `users` поверхностные: копируется карта, но не сами объекты `User`, поэтому это не изолированный снимок состояния.

Решение: один `saveLock`/единый поток сохранения, глубокий неизменяемый snapshot, запись во временный файл и атомарный `move` поверх основного (где файловая система это поддерживает). Аналогичный принцип нужен для backup.

### 2.3. Ошибка получения SHA-256 незаметно отключает проверку по хешу

`Util.getMediaHash()` при `TelegramApiException` пишет лог и возвращает `null` (`Util.java:62–69`). `SetSnapshot.contains(null)` всегда возвращает `false` (`SetSnapshot.java:13–16`), поэтому проверка в `MediaProcessor` не срабатывает по содержимому, а `addToSent(null)` добавляет бесполезный `null` в набор (`MediaProcessor.java:58–63`, `81–85`, `107–108`). При этом `hashFailures` увеличивается только если исключение вышло наружу, но ошибка `GetFile` уже была поглощена в `Util`.

Это fail-open поведение: при проблеме с получением файла бот продолжает принимать контент без проверки SHA-256. Telegram Bot API указывает, что через `getFile` боты могут скачивать файлы до 20 MB; более крупные документы могут пройти парсер, но не пройти получение хеша. citeturn641971search0

Нужно различать `hash unavailable` и реальный хеш. Не записывать `null`, считать ошибку отдельно и явно определить политику: отклонять такую заявку, откладывать проверку или принимать с ослабленной дедупликацией.

### 2.4. Хеширование может надолго блокировать обработчик обновлений

`Util.getMediaHash()` синхронно вызывает `GetFile`, открывает URL через `openStream()` и загружает весь файл в память через `readAllBytes()` (`Util.java:62–76`). Здесь нет явно заданных connect/read timeout, потоковой обработки или ограничения памяти на стороне приложения.

Большой файл или медленная загрузка могут задержать обработку апдейта; несколько одновременных загрузок увеличивают пиковую память. Лучше выполнять скачивание асинхронно в ограниченном executor, считать SHA-256 потоково и задавать timeout/лимит размера. Не следует логировать URL с bot token: при некоторых IO-ошибках полный URL может попасть в текст исключения.

### 2.5. Ошибка одной задачи может навсегда остановить `ProcessorThread`

`ProcessorThread.run()` не перехватывает исключения вокруг `taskScheduler.tick()` (`ProcessorThread.java:17–28`). При этом `BackupTask` и `PublisherTask` превращают `IOException`/`TelegramApiException` в `RuntimeException` (`BackupTask.java:25–31`, `PublisherTask.java:30–41`). Необработанное runtime-исключение завершит рабочий поток. Сам бот может продолжить принимать сообщения, но публикации, резервные копии и восстановление действий перестанут выполняться.

Изолировать выполнение каждой задачи: логировать исключение, задавать retry/backoff и продолжать цикл. Для такого набора задач проще и надёжнее использовать `ScheduledExecutorService`, чем поддерживать собственный scheduler без тестов.

### 2.6. Scheduler рассчитывает ожидание только по задачам, которые уже выполнились

`TaskScheduler.tick()` обновляет `min` только внутри ветки `now >= entry.nextExecution()` (`TaskScheduler.java:24–38`). Дедлайны задач, которые ещё не наступили, не участвуют в выборе следующего пробуждения. Поэтому задача с более ранним будущим дедлайном может быть запущена позже, чем должна. Проблема усиливается, если одна задача выполняется долго: `now` фиксируется один раз до цикла.

Нужно каждый тик находить минимум `nextExecution` по **всем** задачам и вычислять ожидание от текущего `System.nanoTime()` после обработки цикла. Отдельно проверить расписание, когда периоды задач не кратны друг другу.

### 2.7. `/status` может показать устаревшее время ответа

`NetworkMonitor.check()` обновляет `latency` только при успешном `GetMe` (`NetworkMonitor.java:32–43`); при ошибке оставляет предыдущее значение (`44–50`). `Status.execute()` после проверки в любом случае выводит `Check successful` и это поле (`Status.java:32–40`). Во время нестабильной сети команда может показать старую задержку, а не результат текущей проверки.

Нужен явный результат `check()` (успех/ошибка/latency), а в `/status` — отдельное состояние недоступности и время последнего успешного ответа.

### 2.8. Версия сохранения только логируется, но не обрабатывается

`DataManager.load()` обнаруживает различие `SAVE_VERSION`, но затем всё равно возвращает snapshot (`DataManager.java:59–68`). При изменении схемы старый JSON может быть загружен с дефолтными значениями или несовместимыми полями. Нужны миграции `v1 -> v2 -> ...` либо безопасный отказ от загрузки с сохранением исходного файла.

### 2.9. Дублирование сериализации снимка

`DataManager` и `BackupDataManager` почти полностью повторяют сборку `DataSnapshot` (`DataManager.java:27–56`, `BackupDataManager.java:28–64`). Это создаёт риск: при добавлении нового поля один способ сохранения обновят, а другой забудут. Вынести `SnapshotFactory`/`createSnapshot()` в одно место.

### 2.10. История сетевых сбоев и ответы не ограничены по размеру

`NetworkMonitor.networkReports` растёт без ограничения (`NetworkMonitor.java:26–27`, `53–58`), а `/report` собирает всю историю в одно сообщение (`Report.java:34–40`). Telegram ограничивает обычный текст `sendMessage` 4096 символами после разбора entities; длинный отчёт будет отклонён API. citeturn641971search0

Сделать пагинацию, ограничение периода или отправку отчёта несколькими сообщениями/файлом.

### 2.11. Резервные копии могут перезаписать друг друга

Имя backup строится с точностью до секунды (`BackupDataManager.java:24–25`, `28–35`). Если ручная и плановая копии стартуют в одну секунду, они пишут в один путь. Добавить миллисекунды/UUID или sequence number и писать через временный файл.

## 3. Точно есть при определённых условиях

В этом разделе дефекты подтверждаются кодом, но проявляются только при конкретном событии.

### 3.1. Пользователь без `@username` вызывает `NullPointerException`

Telegram username необязателен. `MediaProcessor` получает `getUserName()` и передаёт его в `User` (`MediaProcessor.java:45–55`). Затем вызывает `user.updateUsername(author)` (`56`). Если `author == null`, конструктор сохраняет `username = null` (`User.java:16–18`), а `updateUsername()` после присваивания `null` вызывает `username.equals(name)` (`User.java:35–38`). Это приводит к NPE.

Такой пользователь может не отправить медиа вообще или не попасть в leaderboard, но именно сценарий обработки медиа гарантированно доходит до этой ошибки. Нужно хранить `userId` отдельно, а для отображения использовать `displayName` с fallback на `firstName`/ID; сравнение nullable-строк делать через `Objects.equals`.

### 3.2. Неудачная публикация удаляет элемент из очереди; затем может умереть планировщик

`Publisher.publish()` вызывает `queue.poll()` до сетевого вызова (`Publisher.java:31–37`). Если любой `client.execute(SendPhoto/SendVideo/SendDocument)` выбрасывает `TelegramApiException`, элемент уже удалён из очереди и до `publishedContent.addToSent()` выполнение не доходит (`39–60`). `PublisherTask` оборачивает исключение в `RuntimeException`, а `ProcessorThread` его не перехватывает.

Итог: заявка теряется в памяти и фоновый поток завершается. При этом `Publisher.submit()` уже увеличил счётчик одобренных и добавил ID в `sentContent` до фактической публикации (`Publisher.java:24–29`), поэтому повторная отправка того же контента будет блокироваться как повтор.

Нужны состояния `QUEUED -> SENDING -> PUBLISHED/RETRY`, retry с backoff и сохранение очереди после одобрения. Не удалять единственную копию элемента до успешного результата отправки.

### 3.3. Перезапуск с незавершённой модерацией оставляет «мёртвые» кнопки

`ModerationHandler.submissions` — оперативная `HashMap` (`ModerationHandler.java:20–22`). В `DataSnapshot` поля для этих заявок нет (`DataSnapshot.java:9–24`), а `Main.loadData()` не восстанавливает эту карту (`Main.java:135–160`). При штатном завершении `DataManager.save()` сохраняет набор `onModContent`, но не сами `Submission`.

Если бот перезапустился, пока сообщение ожидало решения модератора, старая inline-кнопка всё ещё может быть нажата, но `submissions.get(id)` вернёт `null`. `approve()` передаст `null` в publisher, а `reject()` попытается вызвать `submission.chatId()`; оба сценария завершаются ошибкой. Сам контент может остаться заблокированным в `onModContent`.

Нужно сохранять pending submissions и идентификаторы moderation message; при старте восстанавливать очередь решений или удалять/помечать устаревшие сообщения.

### 3.4. Отправка медиа из группы использует неправильный chat ID

`MediaProcessor` создаёт `Submission(authorId, messageId, ...)` (`MediaProcessor.java:45–55`), хотя второе поле записи объявлено как `chatId` (`Submission.java:3–10`). Затем `ModerationHandler` вызывает `replyStatus(submission.authorId(), submission.chatId(), ...)` (`ModerationHandler.java:48`, `58`): то есть использует ID автора как ID чата, а ID исходного сообщения — как message ID.

Для личного диалога user ID обычно совпадает с chat ID, поэтому ошибка может быть незаметна. Для группы это разные идентификаторы: реакции на исходное сообщение не сработают. В `MediaProcessor` та же подмена используется напрямую при `replyEmoji(authorId, messageId, ...)` (`67`, `77`, `84`, `91`, `112`). Кроме того, ошибка реакции может прервать метод уже после отправки заявки на модерацию.

Либо явно запретить групповые источники, либо хранить `sourceChatId: long` и `sourceMessageId: int` отдельно и использовать их для реакций.

### 3.5. `UpdateUserTask` может превышать лимит действий

`UpdateUserTask.java:28–30` проверяет, что `actions < cap`, а затем прибавляет весь `maxRecovery`, не ограничивая результат остатком до `cap`. Например, при `cap = 24`, `actions = 23`, `maxRecovery = 2` итог станет `25`; при восстановлении `6` — `29`.

Это достижимо при достаточно высоком рейтинге пользователя. Правильная формула: `actions = Math.min(cap, actions + recovery)`.

### 3.6. Одобрить/отклонить заявку может любой, кто может нажать кнопку в чате модерации

`ModerationHandler.handle()` разбирает callback data и выполняет `approve/reject`, но не проверяет `query.getFrom().getId()` и не проверяет, что сообщение пришло из настроенного moderation chat (`ModerationHandler.java:30–40`). В Telegram `CallbackQuery` содержит отправителя нажавшей кнопки (`from`) и исходное сообщение (`message`). citeturn281990view0

Если в чате модерации есть участники, которым нельзя выдавать право публикации/отклонения, они всё равно смогут нажимать кнопки. Нужно проверять роль по ID пользователя и ожидаемый chat ID до любого изменения состояния. Если доступ к этому чату имеют исключительно доверенные модераторы, риск ниже, но контроль на стороне бота всё равно надёжнее.

### 3.7. Отклонённый контент остаётся помеченным как ожидающий модерации и/или заблокированным по хешу

При поступлении медиа в модерацию код добавляет unique ID в `onModContent` и SHA-256 в `sentHashedContent` (`MediaProcessor.java:104–108`). В `reject()` удаляется только запись из `submissions`; соответствующие элементы из этих наборов не удаляются (`ModerationHandler.java:43–48`).

В результате повторная отправка после отклонения может получить «уже на модерации» либо «повтор». Возможно, это намеренная политика полного запрета повторной отправки отклонённого контента. Если это так, её стоит явно назвать `rejectedContent`/`blockedHashes`; если нет — при reject очищать временный pending-state и отдельно решать, должен ли хеш попадать в permanent blacklist.

### 3.8. Ошибка отправки в чат модерации оставляет частично созданную заявку

`MediaProcessor` сначала увеличивает `appliedContent` и помещает запись в `submissions`, затем отправляет медиа в Telegram (`MediaProcessor.java:102–108`). Если `Main.sendToModeration()` выбрасывает исключение, обработка прерывается до добавления в `onModContent`/`sentHashedContent`, до уменьшения `actions` и до ответа пользователю. В карте остаётся orphan-запись, а статистика уже увеличена.

Нужно определиться с порядком транзакции: сначала подготовить заявку, отправить moderation message, получить его ID, затем фиксировать `PENDING`; при ошибке откатывать предварительные изменения.

### 3.9. Нулевые/отрицательные интервалы в конфиге могут превратить scheduler в busy loop

Конфиг позволяет задать `TEST_NETWORK`, `PUBLICATION_PERIOD`, `USER_PERIOD`, `BACKUP_PERIOD` и их test-аналоги без проверки (`Config.java:7–14`). `TaskEntry.update()` переводит период в наносекунды и прибавляет к текущему времени (`TaskEntry.java:16–19`). При периоде `0` или отрицательном значении следующая дата выполнения уже наступила, и задача может запускаться на каждом проходе цикла, загружая CPU и/или API/диск.

Проверять все интервалы на старте: значение должно быть строго положительным, а единицы измерения — явно документированными.

### 3.10. `/report` перестанет работать после накопления длинной истории

`Report` отправляет всю историю одним `sendMessage` (`Report.java:34–40`). При большом количестве аварий текст превысит 4096 символов — лимит обычного `sendMessage` в Bot API — и Telegram отклонит сообщение. citeturn641971search0

## 5. Идеи и улучшения

### 5.1. Ввести явный жизненный цикл заявки

Сейчас жизненный цикл распределён между `submissions`, `onModContent`, `sentHashedContent`, `Publisher.queue`, `sentContent` и `publishedContent`. Эти структуры могут расходиться.

Лучше сделать одну сущность `Submission` с ID и состоянием:

`RECEIVED -> PENDING_MODERATION -> APPROVED -> QUEUED -> PUBLISHING -> PUBLISHED`

Отдельные конечные состояния: `REJECTED`, `FAILED` (с причиной и числом попыток). Переходы выполнять через методы репозитория, которые атомарно проверяют предыдущее состояние. Кнопки модерации должны быть идемпотентны: повторное нажатие на уже обработанную заявку не начисляет рейтинг и статистику второй раз.

### 5.2. Выбрать простую, но явную модель конкурентности

Для такого бота не обязательно вводить сложную многопоточную архитектуру. Самый простой надёжный вариант — один поток/очередь событий, который изменяет бизнес-состояние, а сетевые и файловые операции выполняются ограниченными executor-ами с результатом, возвращаемым в основной поток. Альтернатива — синхронизированный repository с неизменяемыми snapshot-объектами.

Главное — не смешивать `ConcurrentHashMap`, обычные `HashSet`, изменяемые `User` и внешнюю сериализацию без правил доступа.

### 5.3. Разделить слои

Возможная структура без излишней сложности:

- `telegram/` — разбор Update, команды, callback-и, отправка Telegram API;
- `application/` — сценарии `SubmitMedia`, `ApproveSubmission`, `RejectSubmission`, `PublishNext`;
- `domain/` — `User`, `Submission`, статусы, правила лимитов и рейтинга;
- `persistence/` — репозитории и snapshots;
- `infrastructure/` — scheduler, network monitor, конфигурация, логирование.

`Main` должен только собирать зависимости и запускать приложение. Сейчас он одновременно является контейнером глобального состояния, bootstrap-классом, диспетчером, владельцем сервисов и местом загрузки состояния.

### 5.4. Сделать модерацию безопасной и восстанавливаемой

Проверять ID модератора и ID чата, обрабатывать `null`/неизвестный submission ID, отвечать на каждый callback (включая некорректный), блокировать повторную обработку. Сохранять pending submissions и `moderationMessageId`, чтобы после перезапуска можно было восстановить модерацию.

### 5.5. Сделать публикацию устойчивой к сбоям

Не удалять заявку из durable queue до успешного ответа Telegram API. Добавить ограниченный retry с экспоненциальной задержкой, обработку `429`/`RetryAfter`, отдельное состояние `UNKNOWN`, если запрос мог быть принят сервером, но клиент получил timeout. Полной exactly-once гарантии при сетевом обрыве между сервером Telegram и ботом добиться нельзя без API-идемпотентности; поэтому нужно сознательно выбрать at-least-once или at-most-once поведение и уметь разбирать неопределённые случаи.

### 5.6. Сохранение данных

Для небольшого проекта JSON можно оставить. Но нужно:

- единый `SnapshotFactory`;
- версия схемы и последовательные миграции;
- запись во временный файл + атомарная замена;
- сериализация через единый lock/поток;
- глубокий snapshot без изменяемых ссылок на `User`;
- тесты round-trip для `DataSnapshot` и сценария старой версии;
- регулярная проверка возможности восстановить backup, а не только его создание.

Если состояние/очередь станут критичны, SQLite даст транзакции и индексы без необходимости разворачивать отдельный сервер.

### 5.7. Проверка конфигурации при старте

До регистрации бота валидировать token, `MODERATOR`, `CHANNEL`, положительность интервалов, `ACTIONS_DELTA > 0`, допустимость штрафов/бонусов и согласованность лимитов. Ошибка должна давать одно понятное сообщение и останавливать старт, а не проявляться в произвольном месте позднее.

### 5.8. Тесты, которые дадут наибольшую пользу

Приоритетный минимальный набор:

1. `User.updateUsername(null)` и пользователь без username.
2. Расчёт восстановления действий на границе cap.
3. Одобрение/отклонение одного ID дважды.
4. Поведение после restart при заявке `PENDING_MODERATION`.
5. Ошибка `sendPhoto`/`sendVideo` и повторная публикация.
6. `DataManager.save/load` round-trip, несовпадающая версия и прерывание записи.
7. `TaskScheduler` с непересекающимися периодами и исключением из одной задачи.
8. Ввод медиа из private/group chat.

Сейчас в архиве нет `src/test` с тестами, поэтому эти регрессии ничем автоматически не защищены.
