# Повторный аудит TelegramSuggestionsBot

**Объект:** `bot.zip`  
**Срез:** исходники из архива, состояние на 09.11.2026  
**Объём:** 56 Java-файлов, примерно 2314 строк.  
**Ограничение проверки:** архив содержит `bot/main/java` и `bot/main/resources`, но не содержит `build.gradle`, `settings.gradle`, Gradle wrapper или другого файла сборки. Поэтому полную сборку и проверку зависимостей выполнить нельзя. В отчёте отдельно отмечены дефекты, которые видны непосредственно в исходниках.

## Краткий вывод

Изменения исправили несколько важных проблем предыдущей версии:

- `NetworkMonitor` теперь корректно присваивает время начала простоя.
- `User.updateUsername()` больше не вызывает NPE при `null`.
- `UpdateUserTask` ограничивает восстановление через `Math.min(MAX_ACTIONS, ...)`.
- `ModerationHandler` проверяет наличие у нажавшего callback права `ADMIN`.
- Очередь публикации теперь использует `peek()` и удаляет элемент после успешного ответа Telegram, а не до отправки.
- `DataSnapshot` теперь содержит `submissions`, а `Main.loadData()` их восстанавливает.
- Интервалы конфигурации проверяются на положительность.
- `Status` теперь отображает неудачную проверку Telegram API как ошибку.
- Сборка snapshot вынесена в общий `DataManager.createSnapshot()`.
- Классы `commands.custom.fun` присутствуют в новом архиве.

При этом несколько проблем исправлены лишь частично. Самая крупная системная слабость осталась прежней: состояние хранится в изменяемых глобальных коллекциях и доступно из обработчика Telegram, фонового потока и сохранения. Кроме того, в новом коде появилась некорректная ссылка `message.is` в `MediaProcessor.java:55`.

**Главные приоритеты:** исправить строку `message.is`; закончить исправление scheduler; сделать обработку callback-ов идемпотентной; устранить гонки состояния/сохранений; сохранить pending-заявки при каждом важном переходе, а не только по команде или после публикации.

## 1. Баги, которые точно есть

### 1.1. Некорректный доступ `message.is` в `MediaProcessor.java:55`

```java
Submission submission = new Submission(authorId, message.getChatId(), messageId, author, anon, message.is, media);
```

Здесь код обращается к члену `is` объекта Telegram `Message`. В Telegram Bot API у сообщения есть поле `has_media_spoiler`, но отдельного поля `is` нет. Javadoc `Message` для `telegrambots-meta:10.3.0` также не документирует публичного члена с таким именем. Поэтому в текущем виде это выглядит как ошибка компиляции: класс `Message` не должен разрешить такой доступ.

Если цель — перенести признак спойлера из исходного сообщения, используй соответствующий accessor библиотеки для `has_media_spoiler` (точное имя проверь по установленному JAR/IDE autocomplete). Если исходный спойлер не требуется сохранять, передавай явно `false`.

Источники API: [Telegram Bot API — Message](https://core.telegram.org/bots/api#message), [TelegramBots Meta 10.3.0 — Message](https://javadoc.io/static/org.telegram/telegrambots-meta/10.3.0/org/telegram/telegrambots/meta/api/objects/message/Message.html).

### 1.2. `Report` выводит на одну запись больше лимита

`commands/custom/developer/Report.java:43–45`:

```java
 debug.append(format(...));
 if (++c > ConfigManager.config.MAX_NETWORK_REPORTS) break;
```

Проверка находится после добавления записи. При `MAX_NETWORK_REPORTS = 5` выводятся шесть инцидентов, если в истории их достаточно. Это небольшой, но безусловный off-by-one при достижении лимита. Проверять `c >= MAX_NETWORK_REPORTS` до `append()` либо инкрементировать перед добавлением.

## 2. Баги, которые могут быть

### 2.1. Гонки при работе с общим состоянием остались

Новая версия почти не изменила модель конкурентного доступа:

- `ModerationHandler.submissions` — обычный `HashMap` (`ModerationHandler.java:23`).
- `SetSnapshot` использует `HashSet` и возвращает наружу прямую ссылку через `sent()` (`SetSnapshot.java:7–19`).
- `NetworkMonitor.networkReports` — `ArrayList`, хотя ссылка объявлена `volatile` (`NetworkMonitor.java:26`).
- `User.userTags` — обычный `HashSet`; остальные поля `User` публичные и изменяемые (`User.java:7–12`).
- `UserData.users` — `ConcurrentHashMap`, но потокобезопасность карты не распространяется на объекты `User` внутри неё.
- `DataManager.createSnapshot()` копирует коллекции, пока другие потоки могут их изменять (`DataManager.java:65–73`).

`ProcessorThread` меняет `actions`, `PublisherTask` взаимодействует с очередью, Telegram callback-и изменяют `submissions` и `User`, а `/save`, backup и shutdown hook читают состояние для записи. В зависимости от порядка событий возможны потерянные изменения, `ConcurrentModificationException`, неполный snapshot и рассогласование счётчиков с коллекциями.

Особенно важно: `volatile` у `networkReports` гарантирует видимость замены ссылки, но не делает безопасными `add()`, `size()` и чтение элементов `ArrayList`.

### 2.2. Сохранение по-прежнему не атомарно и не имеет надёжной блокировки

`DataManager.save()` использует:

```java
if (executed) throw new RuntimeException("Save overriding");
executed = true;
```

`executed` — обычный `boolean`, а не synchronized/atomic lock (`DataManager.java:27–40`). Два потока могут одновременно увидеть `false` и оба начать запись. Метод вызывается из `/save`, `PublisherTask` и shutdown hook. Даже если второй вызов увидит `true`, он просто завершится исключением, а не будет ждать/объединять сохранение.

Кроме того, JSON записывается сразу в `data.json`. Аварийное завершение во время записи может оставить повреждённый или усечённый файл. `usersCopy` — поверхностная копия: объекты `User` внутри продолжают изменяться, как и их `userTags`.

`BackupDataManager` использует аналогичный незащищённый `executed` (`BackupDataManager.java:15–34`).

Рекомендуемая схема: один lock или один поток записи, глубокий неизменяемый snapshot, запись в `data.json.tmp`, затем атомарная замена основного файла. Backup должен использовать тот же механизм создания snapshot.

### 2.3. Ошибка получения SHA-256 всё ещё отключает дедупликацию по содержимому

`Util.getMediaHash()` ловит `TelegramApiException`, пишет лог и возвращает `null` (`Util.java:62–69`). `MediaProcessor` воспринимает `null` как обычное отсутствие хеша (`MediaProcessor.java:58–63`, `81–85`, `107–108`). `SetSnapshot.contains(null)` специально возвращает `false`, поэтому при сбое Telegram `getFile` проверка по SHA-256 фактически пропускается.

Есть ещё ошибка статистики: `MediaProcessor` увеличивает `networkMonitor.hashFailures` только если исключение выходит из `getMediaHash()`, но `TelegramApiException` уже поглощается внутри `Util`. Поэтому `/debug` может не учитывать такие сбои.

Это fail-open поведение. Нужно возвращать отдельный результат `hash success / unavailable`, не смешивать его с настоящим хешем и явно определить политику при ошибке: отказать, отложить проверку или принять с пометкой о неполной дедупликации.

### 2.4. Хеширование синхронное, без явных timeout и потокового чтения

`Util.getMediaHash()` вызывает Telegram `GetFile`, затем открывает URL и читает файл целиком через `readAllBytes()` (`Util.java:62–76`). Всё это происходит прямо внутри `MediaProcessor.execute()`, то есть обработка входящего Update ждёт сетевое скачивание.

Медленный ответ или большой файл может надолго задержать обработку апдейта; несколько параллельных загрузок увеличивают расход памяти. Лучше ограниченный executor, connect/read timeout, проверка размера и потоковый `MessageDigest.update()`.

Отдельный риск: URL содержит bot token. Не стоит писать полный URL в логи, поскольку сетевое исключение может содержать URL в своём сообщении.

### 2.5. Обработка исключений в `ProcessorThread` улучшена, но задача не изолируется

Теперь `ProcessorThread.run()` ловит `RuntimeException` вокруг всего `taskScheduler.tick()` (`ProcessorThread.java:19–24`). Это лучше прежнего поведения: обычное runtime-исключение уже не обязано убить поток.

Но если задача выбрасывает исключение, `TaskScheduler.tick()` прерывается на ней. `entry.update()` не вызывается, поэтому её `nextExecution` остаётся в прошлом. На следующем тике эта же задача запускается снова и может снова упасть. Все задачи, расположенные после неё в списке, в этом тике не выполняются. В зависимости от сохранённого `delta` это приводит к повторным попыткам с устаревшей задержкой или к очень частым повторам.

Нужна изоляция каждой задачи: `try/catch` внутри цикла, отдельная политика `retry/backoff`, логирование ID задачи и гарантированное обновление/перенос её дедлайна. Просто поймать исключение вокруг всего `tick()` недостаточно.

### 2.6. Ошибка расчёта следующего пробуждения осталась без изменений

`TaskScheduler.java:24–38` всё ещё обновляет `min` только внутри условия `now >= entry.nextExecution()`.

Пример: задача A должна выполниться через 15 секунд, задача B — через 20 секунд. На отметке 15 секунд выполняется A и планирует себя на 30 секунд. B ещё не просрочена, поэтому не участвует в `min`. Планировщик выбирает 30 секунд и спит 15 секунд, хотя B должна выполниться через 5 секунд.

Нужно считать минимум `nextExecution` для **каждой** задачи. Сама проверка просрочки должна решать только, запускать ли задачу; она не должна решать, учитывать ли её дедлайн при выборе времени пробуждения.

Есть и дополнительный нюанс: `now` берётся один раз до цикла. Если одна задача выполняется долго, другие могут стать просроченными уже во время этого прохода. После цикла следующий дедлайн нужно сравнивать с актуальным `System.nanoTime()`, а просроченные задачи не должны оставаться незамеченными из-за старого `now`.

### 2.7. `SAVE_VERSION` не изменён после изменения структуры snapshot

В новой версии в `DataSnapshot` добавлено поле `submissions` (`DataSnapshot.java:17`), но `Metadata.SAVE_VERSION` остался равен `1` (`Metadata.java:5`). Старый `data.json` от предыдущей версии также имеет `SAVE_VERSION = 1`, поэтому `DataManager.load()` сочтёт его актуальным.

Для старого snapshot поле `submissions` отсутствует и останется пустым. При этом старый snapshot мог содержать `onMod` и `hashed`, поэтому после обновления бот восстановит отметки ожидающей модерации, но не восстановит сами заявки. Это оставит старые moderation-кнопки без соответствующего `Submission`.

Нужно поднять версию схемы и добавить миграцию либо явно обработать старый формат: очистить неподтверждённые `onMod`-элементы, не теряя остальные данные. Сейчас код при несовпадении версии уже останавливает загрузку — это безопаснее молчаливого продолжения, но миграций нет.

### 2.8. `NetworkMonitor.check()` может выполняться одновременно

Проверка вызывается как минимум периодической `DebugTask`, `/status` и `/debug`. Эти вызовы не синхронизированы (`NetworkMonitor.java:32–54`). Одновременно меняются `failures`, `downStart`, `downStartTime`, `latency`, `lastSuccess` и список отчётов.

Из-за этого две проверки могут пересекаться: например, успешный запрос может закрыть простой, пока другой запрос ещё не завершился или уже зафиксировал очередную ошибку. `volatile` не защищает последовательность операций. Стоит сериализовать проверки одним lock/исполнителем или разделить сбор сетевых результатов и обновление состояния.

### 2.9. История сетевых отчётов всё ещё растёт без ограничения

`MAX_NETWORK_REPORTS` ограничивает только число выводимых записей в `/report`. Сам `NetworkMonitor.networkReports` продолжает копить все инциденты в `ArrayList` (`NetworkMonitor.java:26`, `61`). После долгой работы память будет постепенно расходоваться. Кроме того, если администратор задаст очень большое `MAX_NETWORK_REPORTS`, итоговое сообщение всё ещё может превысить Telegram-лимит.

Ограничить саму историю кольцевым буфером/очередью фиксированного размера или хранить её на диске с пагинацией.

### 2.10. Все задачи планировщика запускаются сразу после старта

`TaskScheduler.register()` создаёт `TaskEntry` с `System.nanoTime()` (`TaskScheduler.java:20`), а `TaskScheduler.tick()` считает такую задачу просроченной немедленно. Поэтому на первом проходе запускаются `BackupTask`, `DebugTask`, `PublisherTask` и `UpdateUserTask`, независимо от их `period`.

Для backup/debug это может быть желаемым поведением. Но `UpdateUserTask` сразу восстанавливает пользователям действия. Если период восстановления задуман как реальный cooldown, каждый перезапуск бота даёт дополнительное восстановление, вплоть до `MAX_ACTIONS`. Если это намеренный reset при запуске, замечание не является багом; если период должен сохраняться независимо от рестартов, нужно хранить время следующего восстановления или задавать первый запуск через период.

## 3. Точно есть при определённых условиях

### 3.1. Реакции на исходное медиа из группы отправляются в неправильный чат

`Submission` теперь правильно хранит `message.getChatId()` и `messageId` (`MediaProcessor.java:55`). Это исправило прежнюю путаницу в самой заявке.

Но все вызовы `Util.replyEmoji()` в `MediaProcessor` по-прежнему передают `authorId` вместо `message.getChatId()` (`MediaProcessor.java:67, 77, 84, 91, 97, 112`). В личном чате ID пользователя и чата совпадают, поэтому ошибка скрыта. В группе/супергруппе это разные ID, и Telegram не найдёт исходное сообщение в чате с ID пользователя.

Использовать `message.getChatId()` во всех этих вызовах. Для callback-ответов в `ModerationHandler` уже используется `submission.chatId()` — там эта часть исправлена.

### 3.2. Пользователь без username больше не вызывает NPE, но его имя публикации может стать строкой `null`

`User.updateUsername(null)` теперь подставляет `[unspecified]`, это исправление работает (`User.java:35–39`). Однако `Submission` создаётся раньше, с исходным `author` (`MediaProcessor.java:46, 55`). Если у пользователя нет username и он не включил анонимность, `Publisher.createCaption()` конкатенирует `submission.authorName()` и получит текст `null` (`Publisher.java:68–70`).

Использовать `user.username`/отдельный `displayName` после нормализации либо хранить `authorDisplayName` с fallback на first name или ID.

### 3.3. Callback со старым или неизвестным ID приводит к NPE

`ModerationHandler.reject()` получает `submission = submissions.get(id)`, затем без проверки вызывает `submission.messageId()` (`ModerationHandler.java:43–48`). Если ID отсутствует, callback устарел, заявка уже обработана или старый `data.json` не содержал её — будет NPE.

В `approve()` ситуация аналогичная: `publisher.submit(null, spoiler)` приводит к NPE внутри `Publisher.submit()` (`ModerationHandler.java:51–54`, `Publisher.java:24–28`). Проверять наличие заявки до начала действий; неизвестный ID должен завершаться понятным `AnswerCallbackQuery`, а не падением.

### 3.4. Повторное нажатие или ошибка Telegram API может дважды одобрить одну заявку

В `approve()` сначала выполняется `publisher.submit()` — он увеличивает счётчики и добавляет элемент в очередь. Только после удаления moderation-сообщения и ответа callback удаляется элемент из `submissions` (`ModerationHandler.java:51–63`).

Если Telegram отклонит `DeleteMessage` или `AnswerCallbackQuery`, заявка останется в `submissions`, хотя уже попала в очередь. Повторный callback снова выполнит `publisher.submit()` и добавит дубль, а также повторно увеличит статистику. Похожие гонки возможны при почти одновременном нажатии двумя модераторами.

Нужен атомарный переход из `PENDING` в `APPROVED` до внешних UI-операций. Обработчик должен гарантировать, что только один callback может получить право на переход. Удаление кнопки и callback-ответ — вторичные операции, их отказ не должен повторно одобрять заявку.

### 3.5. Отклонение может удалить заявку из памяти, хотя Telegram-операции не завершились

В `reject()` запись удаляется из `submissions` до удаления moderation-сообщения и отправки ответа (`ModerationHandler.java:43–48`). Если `DeleteMessage` завершится ошибкой, moderation-кнопка может остаться в чате, но связанной заявки уже нет. Последующее нажатие попадёт в сценарий из пункта 3.3.

Изменение бизнес-состояния и удаление сообщения Telegram нужно разделить: сначала атомарно зафиксировать `REJECTED`, а не просто удалять объект; затем пытаться убрать клавиатуру/сообщение. Повторный callback для `REJECTED` должен быть безопасным.

### 3.6. Pending moderation не гарантированно сохраняется при аварийном завершении

`submissions` теперь включён в snapshot и восстанавливается, но `DataManager.save()` не вызывается при каждом добавлении заявки (`MediaProcessor.java:102–112`). Файл `data.json` записывается через `/save`, shutdown hook и после успешной публикации в `PublisherTask`. Если бот получил новую заявку на модерацию, а затем аварийно завершился до следующего сохранения, в `data.json` её не будет.

Плановый `BackupTask` записывает отдельный backup-файл, но `Main.loadData()` загружает только `data.json`; автоматического восстановления последнего backup нет. Поэтому само наличие backup не гарантирует восстановление этой заявки.

Сохранение нужно привязать к переходам состояния или сделать журнал операций. Для JSON-проекта достаточно сохранять snapshot после приёма/одобрения/отклонения, если нагрузка небольшая.

### 3.7. Уже опубликованный дубликат может навсегда заблокировать очередь

`Publisher.publish()` делает `queue.peek()`, а если `publishedContent` уже содержит ID текущего элемента, просто возвращается (`Publisher.java:31–36`). Элемент не удаляется и не переводится в ошибочное состояние. Поэтому вся очередь за ним больше не публикуется.

Такое состояние возможно при дублированном одобрении, неконсистентном snapshot или повторном восстановлении старой очереди. Если ID уже опубликован, элемент нужно удалить/пометить как duplicate и продолжить обработку следующих.

### 3.8. `AdminList` может получить `IndexOutOfBoundsException` при одновременном добавлении пользователя

`AdminList.execute()` создаёт snapshot `userTop`, но цикл ограничивает индекс через актуальный `UserData.users.size()` (`AdminList.java:39–44`). Если после создания списка в карту добавится пользователь, `users.size()` станет больше `userTop.size()`, и `userTop.get(i)` выйдет за границы.

Использовать `i < userTop.size()`. Если обработка апдейтов гарантированно однопоточная, это редкий сценарий, но правильная граница — размер snapshot.

### 3.9. Данные старой версии оставляют старые moderation-кнопки без заявок

Это частный случай проблемы версии схемы из 2.7. Если `data.json` был сохранён старой версией, он может содержать `onMod`/`hashed`, но не содержит новой карты `submissions`. Поскольку версия сохранения не изменилась, новая версия принимает файл как `SAVE_VERSION = 1`. Старые кнопки будут нажиматься, но `submissions.get(id)` вернёт `null`.

## 5. Идеи и улучшения

### 5.1. Ввести состояние `Submission`

Сейчас состояние заявки распределено между `submissions`, `onModContent`, `sentHashedContent`, `Publisher.queue`, `sentContent` и `publishedContent`. Вместо одновременного изменения нескольких коллекций стоит хранить статус в самой заявке:

`PENDING_MODERATION -> APPROVED -> QUEUED -> PUBLISHING -> PUBLISHED`

Отдельные состояния: `REJECTED`, `FAILED`, при необходимости `UNKNOWN` для timeout после отправки. Переходы должны быть атомарными и идемпотентными. Это устранит повторное одобрение, NPE на устаревших callback-ах и часть проблем восстановления.

### 5.2. Разделить бизнес-операцию и Telegram UI

Например, `approveSubmission(id, moderatorId, spoiler)` сначала атомарно переводит заявку в `APPROVED` и ставит её в очередь. После этого отдельная часть удаляет moderation-сообщение и отвечает на callback. Ошибка удаления не должна откатывать уже зафиксированное одобрение и не должна позволять повторить его.

То же для reject: сначала зафиксировать `REJECTED`, затем выполнить необязательное удаление сообщения и реакцию на исходное сообщение.

### 5.3. Выбрать одну модель конкурентности

Для такого проекта не требуется сложная многопоточность. Практичный вариант: один поток владеет изменяемым бизнес-состоянием; сетевые операции выполняются асинхронно/в ограниченном executor, а результат возвращается в этот поток. Альтернатива — repository с чёткими lock-ами и неизменяемыми snapshot-объектами.

Не стоит полагаться на то, что `ConcurrentHashMap` делает потокобезопасными `User`, его `HashSet`, `HashMap submissions` и `HashSet` внутри `SetSnapshot`.

### 5.4. Сделать сохранение надёжным

Для небольшого бота JSON можно оставить. Минимальный вариант:

1. Единый `createSnapshot()` — уже сделано.
2. Глубокая копия объектов/immutable DTO, а не ссылки на изменяемые `User`.
3. Единый lock или отдельный single-thread executor для сохранения.
4. Запись во временный файл и атомарная замена.
5. Версия схемы + миграции.
6. Сохранение после каждого важного перехода состояния.
7. Тест восстановления из старого и нового JSON.

Если очередь публикаций и модерации станет критичной, SQLite будет естественным следующим шагом: транзакции, индексы и durable queue без отдельного сервера.

### 5.5. Доработать publisher

- Если ID уже опубликован — удалить duplicate из очереди и перейти к следующему элементу.
- Хранить попытки и `nextAttemptAt`; применять ограниченный backoff.
- Разделять временные ошибки (`429`, timeout, сеть) и постоянные ошибки (неподдерживаемое медиа, нет прав на публикацию).
- Помнить, что timeout может произойти после того, как Telegram уже принял сообщение: без серверного idempotency key exactly-once гарантировать нельзя. Нужно выбрать at-least-once или at-most-once и явно учитывать состояние `UNKNOWN`.
- При успешной публикации сохранять Telegram `message_id`, чтобы при необходимости можно было ссылаться на опубликованный пост.

### 5.6. Доработать scheduler

Для небольшого числа задач можно оставить собственный scheduler, но он должен:

- учитывать ближайший deadline каждой задачи;
- отдельно обрабатывать исключение каждой задачи;
- иметь retry/backoff;
- не запускать задачи повторно в busy loop;
- явно определять семантику первого запуска: сразу или через период;
- тестироваться на периодах, которые не кратны друг другу (например 15 и 20 секунд), а также на долгой/падающей задаче.

Если особых требований к собственному планировщику нет, `ScheduledExecutorService` уменьшит объём самостоятельно поддерживаемой логики.

### 5.7. Сохранить корректную семантику медиаданных

- В `MediaProcessor` всегда использовать исходный `chatId` для реакций.
- Нормализовать display name до создания `Submission`.
- Явно определить политику `sentHashedContent` при reject: это вечный blacklist или только временная защита от повторов на модерации?
- Если reject не означает permanent ban, удалять `onModContent` и хеш из pending-наборов; если означает — переименовать их в blacklist и хранить отдельное состояние.
- Хешировать файл потоково, ограничивать размер и timeout.

### 5.8. Минимальный набор тестов

1. Пользователь без username: заявка, caption, leaderboard.
2. Медиа из private chat и group/supergroup: реакции ставятся в исходный чат.
3. Approve/reject одного ID дважды и два callback-а одновременно.
4. Ошибка `DeleteMessage`/`AnswerCallbackQuery` после одобрения.
5. Публикация с ошибкой Telegram API, повтор публикации и уже опубликованный ID в голове очереди.
6. Перезапуск с `PENDING_MODERATION` и `QUEUED`.
7. Миграция старого `SAVE_VERSION = 1` в новую схему.
8. Одновременный `/save`, backup и обновление пользовательских данных.
9. Scheduler с периодами 15/20 секунд, долгой задачей и исключением из первой задачи.
10. Hash failure: проверить, что дедупликация не трактует `null` как успешную проверку.

Но ключевая проблема архитектуры не изменилась: нет единого владельца бизнес-состояния и чётких транзакционных переходов для заявок.
